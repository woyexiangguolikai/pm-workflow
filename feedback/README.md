# 反馈层 —— 工作流自我改进的机制

## 这个目录解决什么

固定编排只能保证「**不出结构性错误**」，保证不了「**内容好**」。
一份平庸但格式完整的产出，能通过原有全部结构检查。

> **测量什么就得到什么。没被测量的质量，等于没有质量。**

---

## 目录与加载方式

| 路径 | 内容 | 加载方式 | 进仓库？ |
|---|---|---|---|
| `rubric/<阶段>.md` | 质量标尺（A 类可脚本化 + B 类需人判） | **常驻注入**，每阶段 ≤10 条 | ✅ |
| `anti-patterns.md` | 反例库 | **常驻注入**（必须限长） | ✅ |
| `checks/*.py` | A 类判据的检查器 | 运行时执行 | ✅ |
| `ANCHORING.md` | 不一致锚定规则 + B→A 升级路线 | 遇到冲突时读 | ✅ |
| `<项目>/feedback-review/*.report.md` | 单次评审记录 | 留档 | ❌ 产出 |
| `<项目>/feedback-review/review-log.jsonl` | 评审流水 | 去重与失效判定 | ❌ 产出 |

**为什么区分常驻与按需**：知识库会随时间增长。常驻部分必须是**小而热**的判据；
大的案例只在你主动检索时才进上下文，否则库越大、每次运行越慢。

**为什么区分「进仓库」与「不进」**：见下面「产出写到哪」一节 ——
这是本仓库最重要的一条结构性约定。

---

## 每次运行的闭环（每阶段末尾执行，不可跳过）

```
阶段产出 → 按 rubric 自评 → 人评（只看打问号的项）→ 提炼 → 写回本目录
```

1. **自评**：逐条给证据，**不许写「已满足」三个字**。
2. **人评**：**只处理自评打问号的项**。这是让「人工兜底」可操作的关键 ——
   否则人要把产出从头看一遍，兜底就变成了瓶颈。
3. **提炼**：把本次产生的**新判据**与**新反例**写回 `rubric/` 与 `anti-patterns.md`。
   **产出不进库，提炼物才进库** —— 存产出不会让它变好，存判据才会。
4. 下次运行时，rubric 与 anti-patterns 自动注入，产出被上一轮的教训约束。

---

## 两条防退化规则

1. **限长**：rubric 每阶段 ≤10 条，超了合并同类项；案例卡不进常驻上下文。
2. **失效**：`review-log.jsonl` 记录每条判据的来源与命中次数。长期不命中、
   或业务已经变了的判据**删掉** —— 旧判据会把新产出带偏。
   **没有失效机制的知识库，会从资产退化成负债。**

## 🔴 产出写到哪（本体与产出的分界线）

**这是本仓库最重要的一条结构性约定。**

| | 放哪 | 进 git？ |
|---|---|---|
| **判据本体**：`rubric/` `checks/` `anti-patterns.md` `ANCHORING.md` `README.md` | `feedback/`（skill 内） | ✅ **是** —— 跨项目复用 |
| **产出**：单次评审报告、评审流水、锚定结论、现状页 | **项目目录**（如 `<项目>/feedback-review/`） | ❌ **不是** —— 逐项目的 |

**为什么必须分开**：

1. **本体要发布，产出不能发布。** 产出里含真实业务参数（阈值、比例、渠道、内部文件清单）——
   那是项目的资产，不是工作流的资产。
2. **生命周期不同。** 本体是长期资产（要维护、要做失效判定）；产出是历史记录，看完就归档。
3. **反馈层自己的纪律就是这个**：「**存产出不会让它变好，存判据才会**」——
   把产出留在本体目录，等于违反自己的规矩。

> ⚠️ **曾发生过一次真实的事故**：一次发布前自检报了 `0 BLOCK`，看起来干净 ——
> 但那份自检**只扫密钥 / PII / 本机路径，扫不到商业 know-how**。
> 当时一份 224 行的项目复盘（含真实阈值、分账比例、付款通道、内部文件清单）
> 就在待发布目录里，**自检一句没提**。
>
> → **「通过」只证明被检查过的那几类没问题，不证明没问题。**
> → 现已补一道**项目词黑名单**扫描（见 `scripts/publish-denylist.txt`）。

## 各阶段判据一览（防重复报警）

| 阶段 | 报什么 | 刻意**不**报什么 |
|---|---|---|
| 01 需求 | 编号连续性、汇总一致性、**引用形态合法性**、例外清单自洽 | 卡片是否跟上了上游 |
| 02 PRD | 编号、EARS 句式、三列非空、字段名泄漏、可追溯覆盖率 | 功能点是否覆盖了它 |
| 03 设计 | 主色单一事实源、token 复制、深色主题覆盖、对比度、游离色值 | 原型是否用了这些 token |
| 03b 素材库 | front matter 齐全、id 与类型前缀规范、**许可白名单（唯一「拦截」型判据）**、索引与文件一致、可检索性（tags / 摘要）、`usedBy` 指向真实项目 | 素材本身设计得好不好看（那是 03 的事）；项目里是否真的用了它 |
| 04 原型 | JSX 嵌套、离线包可达、页面数与声明、五端齐备 | 页面对应的需求是否真存在 |
| 06 卡片 | **与上游一致性**（编号 / 优先级 / FR / 页面号）、卡内六段齐全 | 引用本身是否合法（那是 01 的事） |

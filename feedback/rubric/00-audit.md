# 00 盘点 · 质量标尺（rubric）

> **怎么用**：本文件在 00 阶段**常驻注入**。A 类由 `checks/check-audit.py` 自动判；
> B 类由自评**逐条给证据**，人评**只处理打问号的项**。
>
> **本阶段判据的重心**：盘点的产物是**后续所有阶段的对照基线**。它盘漏了一项，
> 01 需求就不会有那条需求，02 PRD 不会有那条规则 —— 而且**没人会发现**，
> 因为下游只能看到「上游没给的东西」，看不到「本来就该有的东西」。
>
> **判据上限 10 条**。超了就合并同类项—— 判据膨胀等于没有判据。

---

## 🔴 00 的特殊性：它是唯一「可以合法为空」的阶段

全新项目走 00 时，存量盘点结果就是空的。**这是正常的，不是缺陷。**

所以本rubric 的判据分两段生效：

| 项目性质 | 判据生效范围 |
|---|---|
| 全新项目（references 第 61–69 行） | 00 可免 → **只跑 A1 / A5**（结构与声明自洽），B 类全免 |
| 存量改造 / 存量扩展 | A/B 全跑 |

**为什么必须显式声明项目性质**：不声明，判据无法知道该不该报缺失 ——
对全新项目报「漏盘了支付回调」是纯噪音，而噪音是判据失效的头号原因。

## A 类 · 可脚本化（必须自动判，不许推给人）

| 编号 | 判据 | 判定线 | 怎么判 |
|---|---|---|---|
| A1 | **数据源结构完整**：每个模块都有 `features` 数组，每条功能有 `id`/`name`/`status` | 0 处缺失 | 逐层遍历，缺字段即报 |
| A2 | **功能点编号连续唯一**（每模块内`AM-01…` / `MU-03…`） | 无缺号无重复 | 按模块前缀分组现算 |
| A3 | **`status` 取值在闭集内**（新增 / 改造 / 保留 / 待定） | 100% | 扫取值列 |
| A4 | **盘点项数 == 视图声明数** | 现算一致 | **两侧都从 `audit.json` 现算**，不读HTML 里的字面量 |
| A5 | **项目性质已声明**且与内容量自洽 | 声明存在，且「存量」但 0 条存量功能 → 报 `warn` 不报 `fail` | 读 `nature` 字段 |
| A6 | **新增/改造项必须有下游落点**（可跨阶段查） | 0 处无落点 | 盘点项的 `id` 在 `requirement.json` / `prd.json` 里查得到 |

**A4 为什么两侧都现算**：视图里的数字如果是从数据源渲染出来的，两侧必然相等，
A4 就永真；如果是人写上去的，就可能漂移。所以判据要检查**视图里的数字是否等于现算值**，
而不是「两边都是同一个来源」。**永真的判据等于没有判据**（元规则 1）。

**A6 是本阶段最重要的一条**：references第 35 行明确要求「新增/改造的功能必须在后续阶段有落点」。
但它**跨阶段**，所以 00 阶段跑的时候通常查不到下游 —— 判据要在 01/02 阶段**回补跑一次**。
这不是缺陷，是阶段顺序的客观事实；把「回补跑」写进 rubric，比让检查器在 00 阶段假装能判要诚实。

## B 类 · 需人判（判据必须可核对）

| 编号 | 判据 | 怎么算不过 |
|---|---|---|
| B1 | **功能地图覆盖完整**：现网能做的每件事都有归位 | 抽查 3 条现网操作，在地图上找不到即不过 |
| B2 | **数据表清单只进技术视图**，未泄漏进业务侧产物 | 表名出现在功能说明 / 需求描述里即不过 |
| B3 | **角色与权限写明**：谁能做什么，不写「系统自动处理」 | 出现「系统自动处理」即不过（与 SKILL.md 端枚举同纪律） |
| B4 | **已知问题有证据**：每条都指向具体位置（表 / 接口 / 页面 / 现象） | 写「历史包袱有问题」而无指向即不过 |

**B2 为什么单列**：盘点阶段会大量读表结构，读完之后表名很容易顺手写进功能说明。
而 PRD 的 A5 判据明确禁止字段名 / 表名泄漏—— **上游放进去的东西，下游禁不住**。

## 元规则（管 rubric 自己）

1. **能一眼判真假的才是判据，判不了的只是口号。**
2. **写完任何 A 类判据必须做变异测试**（`--selftest`）：好样本全绿 **且** 坏样本全红。
3. **假阳性必须改判据，不能靠人工忽略。**
4. **判据不许认识某一个项目的端名 / 模块名 / 表名。** 认识了就等于给下一个项目埋雷——
   详见 `01-requirements.md` A6 的踩坑记录：那里的检查器曾硬编码一份端名白名单，
   换项目后好文档100% 假阳性。**这是本工作流已犯过的错，00 不得重犯。**
5. **变异样本要挑「判据覆盖不到的地方」，不是「判据已经能过的样本」。**
   样本照着代码的假设挑 → 变异测试假绿（AP-06）。

### 本阶段最容易犯的一个错：把「查了什么」当成「盘了什么」

查代码是有产出的（读了 12 张表、追了支付回调），但**读到什么不等于盘出功能**。
判断标准很硬：**能不能用一句业务话描述这件事，且能归到某个功能点上？**
不能，就只是「看过了」。

反过来说，盘点阶段最容易漏的是**不起眼但天天在用的东西**：
后台的导出按钮、运营手工改数据的入口、藏在配置里的开关。这些往往没有独立页面，
读代码时扫过去就没了，但它们是现网真实存在的能力 —— 漏掉它们，改造方案就会漏掉它们。

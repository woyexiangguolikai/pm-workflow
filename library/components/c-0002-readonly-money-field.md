## 一句话

金额字段分两类，**视觉上必须能区分**：**只读下发值**（权威）与 **前端估算值**（仅供参考）。

## 什么时候用

- 一切涉及钱的界面：购物车、确认订单、账单、分账明细、对账、退款金额。
- **尤其是**：优惠计算、分摊、比例抽佣这类「看起来可以就地算一算」的地方。

## 什么时候别用

- 纯展示的统计看板（只读数字，无「估算」概念）—— 不必加区分标记。

## 为什么这条值得进库（本项目强约束的组件化落地）

资金链路的铁律是：**金额一律整数分存储、禁止浮点；由服务端统一计算下发，任何端不得本地自造或二次计算。**
规则写在文档里没人记得住，**做成组件就记得住** ——
组件层直接让「前端自己算个金额展示出来」这件事变得**不舒服**。

## 实现要点

1. **只读值**：直接渲染服务端下发的整数字段，`(分/100).toFixed(2)`。
   ⚠️ 不要在组件里接受「元」为单位的入参 —— 那会引诱调用方先在前端做除法。
2. **估算值**：必须带视觉标记（虚线下划线 / 前缀「约」/ 灰字），
   且**必须与只读值视觉上不同**。用户看到「¥12.30」是不带问号的，看到「约 ¥12.30」才会怀疑。
3. **两值并列出现时**，只读值优先展示且不可被估算值覆盖。
4. **舍入口径不在前端实现**：全部取服务端下发的最终值。
   若业务确需前端预览，预览值必须允许与最终值不一致，**且差异提示要写在界面上而不是靠用户发现**。
5. **禁用浮点中间量**：组件内部不做 `parseFloat` 后再运算。

## 无障碍

- 金额的「约」等修饰词必须进入可访问名（不要用纯 CSS `::before` 装饰，
  读屏会读成没有修饰的数字）。
- 千分位用 `Intl.NumberFormat`，不要手写补逗号（会与读屏的数字读法冲突）。

## 依赖

- CSS 变量建议：`--text-1`（只读值）、`--text-3`（估算值）、`--warn-500`（差异强调）。

## 反面参照

- 反例一：前端 `reduce` 求和展示「合计」—— 与后端差 0.01 就是资损争议的开端。
- 反例二：把 `0.1 + 0.2` 的结果直接 `toFixed(2)` —— 浮点误差被四舍五入掩盖，看起来是对的。

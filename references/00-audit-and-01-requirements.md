# 00 盘点 / 01 需求

## 00 盘点

**触发**：「盘一下这个系统」「存量系统没有文档」「反向梳理」
**产出**：`audit.json` + `audit.html`

### 两种输入

| 输入 | 怎么做 |
|---|---|
| 有源码 | **反向盘点**：读路由 / 数据表 / 枚举类，反推功能清单 |
| 有现网 | 走一遍关键路径，记录实际行为 |

### 盘点要盘到什么

- **功能地图**：模块 › 功能，标注新旧（新增 / 改造 / 保留 / 待定）
- **数据表清单**：表名 + 用途 + 关键字段（**只进技术视图**）
- **角色与权限**：谁能做什么
- **已知问题**：现网的坑、口径不一致、历史包袱

### 查代码的入口（本类项目的通用套路）

| 想查什么 | 去哪 |
|---|---|
| 状态/类型枚举 | `**/enum/**` |
| 支付成功分发 | `**/service/**/paysuccess/**` |
| 结算与折扣 | `**/service/**/settled/**` |
| 表结构 | `数据库/init.sql` 或 migration 目录 |

### 校验

- 盘点项数 == 数据源项数（现算）
- 每个模块至少一个功能
- 新增/改造的功能**必须在后续阶段有落点**（可跨阶段查）

## 01 需求

**触发**：「理需求」「需求清单」「需求澄清」
**产出**：`requirement.json` + `requirements.html`

### 需求清单的组织

层级与 PRD 对齐（**模块 › 功能 › 需求**），但**粒度更粗**：
需求清单回答「**要做哪些事**」，PRD 回答「**每件事怎么做**」。

每条需求至少要有：

| 字段 | 说明 |
|---|---|
| `id` | `RQ-xxx` |
| `title` | 一句话（**业务语言**） |
| `module` / `feature` | 归属 |
| `priority` | P0 / P1 / P2 |
| `ends` | 涉及端（固定枚举） |
| `source` | 来源：客户原话 / 盘点发现 / 合规要求 |
| `status` | 新增 / 改造 / 保留 |

### 第 0 问：项目性质（接到需求先问这个，再谈任何细节）

**全新项目 / 存量改造 / 存量扩展** —— 三选一，它决定后面所有阶段的走法：

| 判定 | 00 盘点 | 影响什么 |
|---|---|---|
| 全新项目 | 可免 | token / 规范由 03 现定，无存量可复用 |
| 存量改造 | **必做** | 功能地图标「改造」，PRD 只写差异，现网行为是基线 |
| 存量扩展 | **必做** | 功能地图标「新增」，且新增功能必须能在现网找到挂靠点 |

**不问这一句就开工 = 最大的需求偏移源**：把改造当新项目会重复造轮子，把新项目当改造会被旧结构绑架。

### 🔴 澄清协议：12 个问题域（问哪个，由「还没确认的域」决定）

**问题不是为问而问。每个域标了消费方 —— 答不上来的域，下游那个产物一定写不实。**
这张表就是「该问什么」的完整清单；澄清 = 把 12 个域全部走到「已确认」或「显式挂起」。

| # | 域 | 必问的问题 | 答案落到哪 |
|---|---|---|---|
| 1 | 项目性质 | 新项目还是改造？本次范围的边界在哪？ | 00 是否必做、需求的 status |
| 2 | 业务目标 | 上线后**谁**在**什么场景**用它？「做成了」怎么衡量？ | 需求卡片「定位」 |
| 3 | 用户与角色 | 有哪几类人？权限差异？谁审批谁复核？ | 逐端职责、PRD 执行方 |
| 4 | 端范围 | 用户在哪端操作？管理端/商家端要不要跟着动？ | 端枚举 |
| 5 | 主流程 | 正常情况一步步怎么走？谁在哪个端做什么？ | 「过程」三列 |
| 6 | 分支与异常 | 每步失败 / 取消 / 超时 / 重复提交怎么办？余额不足、断网呢？ | 「规则」+ 流转出口 |
| 7 | 业务规则 | 金额上限、时间窗、次数限制、互斥条件？ | `BR-xxx` 条款 |
| 8 | 数据与口径 | 每处显示什么数？来源与口径（实时/缓存/快照）？取不到显示什么？脱敏要求？ | 字段 8 项、展示与输入 |
| 9 | 输入约束 | 每个输入框允许输什么？长度 / 格式 / 键盘类型 / 去空格 / 边界行为？ | 输入约束清单 |
| 10 | 关联与影响 | 动了这个，哪些模块受影响？要不要同步改？ | 需求卡片「关联」 |
| 11 | 非功能 | 性能、并发、合规、审计有什么硬要求？ | 附录区 |
| 12 | 上线与迁移 | 存量数据怎么办？要不要灰度？谁验收、拿什么验收？ | 验收清单 |

### 追问节奏（苏格拉底式：不许一次问完，更不许不问）

- **第 1 轮固定**：第 0 问 + 域 2 / 3 / 4 的高层题（共 3–4 题）。**拿到回答前不建目录、不写任何产物。**
- **之后每轮 3–5 题**：优先挑「还没确认的域」里对当前阶段最致命的；每题给推荐选项 + 理由（`AskUserQuestion`，推荐项放第一位）。
- **用户说「你看着办」**：不许自行拍板了事 —— 把默认决策列成清单让他点头，点头结果记入 clarify-log。
- **不许用假设填空**：任何「我默认 XX」必须显式写进 clarify-log 的「假设」区等确认。**假设进入产物而未确认 = 需求偏移已经发生。**
- **偏移信号**：用户开始纠正你（「不是这个意思」）出现第二次时，停止产出，回到澄清。

### 🔴 澄清闸门（过不了不许进 02）

逐轮落盘 `01-requirements/clarify-log.md`（或 `.json`）：轮次 / 问题 / 回答 / 落到的产物。过闸三条：

1. 12 域每个都是「已确认」或「显式挂起（写原因 + 谁拍板）」—— **「没问到」不算一种状态**；
2. 假设区为空，或每条假设都有用户确认记录；
3. 每条需求的 `source` 能追溯到某轮问答（如「客户原话 R2Q3」）或盘点发现。

**没过闸就写 PRD = 把自己的猜测写进需求，后面全错。**

### 每轮 3–5 题、每题给推荐选项

用户明确要求的工作方式：

> 追问每轮 3–5 题、每题给推荐选项。

用 `AskUserQuestion`，每题 2–4 个选项，**推荐项放第一位并标注「（推荐）」**。

**不要**：
- 一次抛 10 个问题
- 自己拍脑袋替用户决定
- 问「你要不要 XXX」这种没有信息量的问题

**要**：先自己按最佳实践拟一版，把「我建议 X，理由 Y，备选 Z」摆出来让用户挑。

### 🔴 来源要留痕

每条需求记 `source`。**「客户说的」和「我推测的」是两种东西** —— 后续开发质疑时要知道找谁对。

### 校验

- **澄清闸门三条全过**（12 域无「没问到」、假设全确认、source 可追溯）—— 此项不过，后面的校验不用跑
- 需求数 == 数据源数（现算）
- 优先级分布、端分布现算
- `source` 非空率 100%
- 每条需求在 PRD 里有对应条款（跨阶段闭环）
- 视图不漂移

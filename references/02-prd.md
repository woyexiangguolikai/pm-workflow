# 02 PRD —— 需求规格说明书

**产出**：`prd.json`（数据源）+ `PRD.md`（给人读的文档）+ `PRD.html`（双视图） + `build-view.py` / `build-doc.py` / `check-biz-lang.py`

---

## 1. 需求规格卡片模型（核心）

层级：**模块 › 功能 › 需求**。

**每条需求是一张自包含卡片** —— 看一条不用翻别的章节。六分区：

| 分区 | 含什么 |
|---|---|
| **定位** | 需求描述 · 优先级 · 涉及端×职责 · 归属 |
| **前置** | 功能前置 / 数据前置 · 上下游依赖 |
| **过程** | 主流程（**执行方│做什么│说明 三列**）· 异常与分支 · 交互说明 · **动效与微交互** · **页面展示字段** · **输入限制** · 页面流转 |
| **规则** | 业务规则 · 状态联动 · 数据展示与来源 · 权限 |
| **关联** | 字段 · 接口 · 流程图 · 原型锚点 |
| **产出** | 输出 · 后置条件 · 验收标准 · 待确认 · 风险 |

### 主流程必须三列

两列**无法表达纯服务端步骤**（定时任务、对账）。

```
执行方        │ 做什么                    │ 说明
用户小程序     │ 点击"确认绑定"            │ 校验中按钮置灰，防重复提交
服务端        │ 调用一卡通绑定接口         │ 超时 5s 重试 1 次
服务端        │ 写入绑定关系              │ 幂等键：卡号+用户id
```

**执行方用端枚举**；技术细节挪进「说明」列。

### 动效 5 项

**转场 / 微交互 / 反馈 / 时长与缓动 / 无障碍降级**。

逐条**只写特有部分**；通用基线放 `prd.json` 的 `appendixMotion`（不要 42 条各抄一遍）。

### 字段 8 项规格

**业务名 + 类型长度精度 / 必填 / 默认 / 约束 / 取值校验 / 脱敏 / 示例 / 变更**。

### 展示与输入（最易漏，必须有）

- **每个位置**显示哪个字段、什么格式、怎么脱敏、**取不到时显示什么**
- **输入框**：键盘类型、长度、允许字符、去空格与全角转半角、边界行为、**提示文案原文**

统一口径：
- 金额余额 **2 位小数、四舍五入到分**
- 手机号 11 位中**四位脱敏**
- 卡号仅**后 4 位**

### 端枚举（固定）

```
用户小程序 / 管理后台 / 收银端 / 商家端 / 服务端
```

## 2. 写作红线（七条，逐条都可能被检查）

1. **逐端写职责，禁「系统自动处理」** —— 说了等于没说，开发不知道谁写这段代码。
2. **提示文案写原文** —— 不要「提示用户失败」，要写「绑定失败，请稍后重试」。
3. **数据展示写来源 + 口径（实时/缓存/快照）+ 兜底** —— 三者缺一，开发和测试的理解就会分叉。
4. **输出与后置条件分开** —— 输出是「返回了什么」，后置条件是「数据库/状态因此变成了什么」。
5. **状态联动双向写** —— 「A 变则 B 变」也要写「B 变时 A 怎么处理」。
6. **页面流转必写出口** —— 成功 / 失败 / 取消**各去哪、带什么参数**。
7. **业务文案里不出现**：表名、字段名、页面路径、接口编号、原型锚点。

> 🔴 第 7 条要靠脚本守，不能靠自觉 —— `note` / `preconditions` 里手写「见 SVC-009」会泄漏到业务视图。

## 3. 双视图（业务 / 技术）

**同一处渲染 `.biz-only` / `.tech-only` 两份**，CSS 切 `body.biz` / `body.tech`。
**不重渲染、不丢信息。** 默认业务视图，状态存 `localStorage`。

数据源拆法：

| 双视图位 | 数据源字段 |
|---|---|
| 字段 | `fields[].business` + `table` / `column` |
| 数据展示 | `dataShow[].source` + `sourceTech` |
| 接口 | 顶层 `interfacesBusiness` |

### 布局：左侧目录树 + 右侧纵向滚动卡片

**不要用平级页签**（用户明确说可读性差）。跨需求的信息放**附录区**。

### 流程图必须图示化

- **HTML**：纵向流程链（序号圆点 + 泳道色标 + 箭头），技术细节放 `techNote`
- **Markdown**：Mermaid `flowchart TD`，`classDef` **只设 `stroke` 不设 `fill`**（设 fill 会盖掉主题色）

## 4. 脚本

| 脚本 | 作用 |
|---|---|
| `build-view.py` | `prd.json` → `PRD.html` |
| `build-doc.py` | 幂等重生成 `PRD.md` 的 `<!--GEN:-->` 块 |
| `check-biz-lang.py` | **业务语言守卫**：Edge 无头渲染 → 剔除 `.tech-only` 子树 → 10 类正则查残留 |
| `_expand_lib.py` | 批量展开功能节点 |
| `_finalize.py` | 补齐（见下方坑 ②） |

模板见 `assets/templates/02-prd/`。

---

## 5. 三个坑

### ① 散文里不能手写接口编号

`note` / `preconditions` 里写「见 SVC-009」会**泄漏到业务视图**（业务视图里不该有接口编号）。
有专门的守卫脚本查这类残留。

### ② `_expand_lib.recompute` 不回写功能节点状态

批量展开后功能节点的状态是旧的 → **必须用 `_finalize.py` 补一遍**。

### ③ `PRD.md` 第 4 章是手写静态文本

决策改定后**必须手动对齐**，否则会出现**互相打架的条款**（第 4 章说 A，生成块说 B）。

> 凡「一部分自动生成、一部分手写」的文档都有这个风险。写完在目录里留一行提醒。

## 6. 校验要点

| 查什么 | 怎么查 |
|---|---|
| 卡片数 = 数据源卡数 | 现算，不写死 |
| 六分区齐全 | 逐卡查 `sections` 的 key 集合 |
| 主流程都是三列 | 查每个 step 的行长度 |
| 端枚举合法 | 查执行方是否都在固定枚举里 |
| 业务视图无技术标识 | `check-biz-lang.py`（**且做变异测试**：故意塞一个表名进去，必须变红） |
| 章节编号连续 | 从数据源现算 |
| 视图不漂移 | `PRD.html` 与 `prd.json` 逐字比对关键字段 |

⚠️ **业务语言守卫最容易做成假检查** —— 见 `references/verification.md` §1 的反例。
检查时**样本必须挑非锚点的 `.t-only` 元素**，且**样本为 0 判失败**。
